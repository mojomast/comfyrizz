# Super Easy: 24-hour submission reliability plan

Decision date: 2026-10-29. This supersedes the repeated original-Pérez retry strategy, not the original campaign evidence. New simplified briefs are separate experiments, never claimed as completions of the original films.

## Submission objective

Deliver a small set of attractive, reproducible, end-to-end Super Easy films. A mode is not submission-ready merely because its package validates or a CPU test renders. Count a success only after proposal, review, approval, production, export, **Download**, and playback. Record the actual limits of the demonstration.

The [official event](https://comfy.org/open-source-higgsfield/) closes **October 30 at 09:00 PT (16:00 UTC)** and is explicitly about apps built with ComfyUI. **Updated user requirement: every production video must use ComfyUI with at least one officially verified hackathon model.** This supersedes the earlier plan for a single generated anchor alongside CPU-only final films. Existing CPU experiments remain diagnostic evidence, not compliant final deliverables. Each new final film needs real generated media contributing to the rendered result, with trusted workflow/model/job/output evidence. Pending jobs, orphan assets and model-authored provenance do not count. Native text/charts/finishing can accompany that contribution. Official ecosystem bonuses name LTX, FLUX 3 and MiniMax H3 and require the relevant model to be core to the workflow; a single asset alone does not establish bonus eligibility. The requirement is assigned to the active Pi migration for planning and shared export enforcement. Existing credit authorization and approvals remain in force; no new GPU spend has been started by this change.

## Current diagnosis

1. **Brief/capability mismatch.** The original showcase requests physical letter interactions, a Penrose illusion, 190 individually meaningful race results and a camera pullback, multi-shot olive physics, singing, and a photographic cat escaping a page. Several are beyond currently demonstrated renderer or generation capabilities.
2. **Planner complexity and conflicting completion rules.** CPU planning has a four-SVG asset floor even when a native layout can communicate the requested result. Historical repair generated unrelated assets and introduced new source-wall failures. Investigate and remove arbitrary quotas in favor of actual scene requirements.
3. **Source correctness is separate from schema correctness.** Correct tiles have coexisted with false narration, mislabeled counts and invented metadata. Source-derived computation helps numbers, but cannot certify arbitrary prose.
4. **Narration is a measured scheduling constraint.** Shorter scripts and fewer scenes reduce risk. Word counts are estimates; use Kokoro measurements and the existing revision path. Do not silently stretch duration or speed up speech.
5. **Repair has been too broad.** Targeted, revision-pinned edits are better than full rebuilds. Known scene and attachment IDs belong in server code, not model guesses. Retain stale-source and approval checks.
6. **Test evidence has been incomplete.** Rolling event tails, missing failed drafts, closing sessions before recovery, and waiting for Download without clicking it concealed useful causes. An MP4 audio stream is not proof of an audible, well-timed soundtrack.
7. **Too much effort went into one stress test.** Repeated full Pérez attempts did not establish reliability across modes. Pause that original brief until a smaller data film and other mode baselines work.

## Testing and stop rules

- First pass: one attempt and at most one normal UI correction per reduced brief. Move to the next mode when it fails; log the cause.
- Use separate planning, narration and export deadlines. Suggested initial CPU deadlines: 180 / 180 / 300 seconds. Report resource limits if export cannot fit that deadline.
- Preserve the same browser and runtime through a correction; use fresh sessions for repeatability tests.
- Before approval: check exact copy, source facts where applicable, planned duration, required visuals and actual pending jobs.
- After export: click Download; verify decoding, exact requested duration within one output frame, opening and ending, legible text, intended motion, and the whole film at normal speed. Listen where audio playback is available; otherwise mark listening unverified.
- One full success earns **candidate**, not **reliable**. A shortlisted mode needs two fresh-session passes, plus a tested recoverable failure, before a reliability claim. This is a submission gate, not a statistical reliability estimate.
- Keep audio-free technical smoke tests separate from showcase films that require sound.
- No more than one targeted product fix per blocker before reassessing payoff across modes. A failed ambitious prompt does not prove the entire mode is unusable.
- All GPU usage remains under the existing shared 60-credit ledger, normal approvals and one-candidate rule. Model-provider token usage is recorded separately; no exact dollar claims without billing evidence.

## Time allocation from this decision

1. **Hours 0–3:** cross-mode baseline tests, contract audit, reduced prompts, and generated-backend readiness. Fix at most the highest-value cross-mode blockers.
2. **Hours 3–8:** complete and review the strongest 2–3 candidates, including one modest ComfyUI anchor if the backend is ready; one small Data Story and conditional uploaded-media test.
3. **Hours 8–14:** repeat finalists from fresh sessions, test recovery and export; promote additional modes only if they complete.
4. **Hour 14:** freeze showcase scope. Cut modes without a completed, reviewed output; no new major capabilities.
5. **Hours 14–20:** final audiovisual polish, posters, provenance, full relevant checks, demo recording and reliable media access.
6. **Hours 20–24:** buffer for packaging, submission copy and verification. Preserve the user's no-commit/no-push/no-deploy constraint unless changed explicitly.

## Research informing the approach

- [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents): predictable workflows for decomposable tasks, routing for distinct task classes, simple tool interfaces, measurable evaluation and stopping conditions. Applied here: mode-specific work and bounded tests instead of open-ended repair.
- [OpenAI, Function calling](https://developers.openai.com/api/docs/guides/function-calling): compute known arguments in code, expose a small relevant tool set, use precise schemas and actionable results. Applied here: server-bound scene/source IDs and fewer irrelevant tools. Provider-specific strict schemas must be verified against the configured provider; OpenAI support is not proof of DeepSeek support.
- [DeepSeek API documentation](https://api-docs.deepseek.com/): current canonical Flash model is `deepseek-flash`; legacy Flash names route to the current service. Changing an alias is not a meaningful model comparison. A model comparison must use distinct supported models on the same frozen brief and app path.
- [LTX prompting guide](https://docs.ltx.io/open-source-model/usage-guides/prompting-guide): start with focused action, consistent lighting and clear camera language; complex physics remain uneven and critical lettering should be composited. Applied here: a single-shot action probe rather than olive/tray multi-shot continuity. Model documentation does not establish which audio or multi-shot features our installed workflow supports.

Research accessed 2026-10-29. These are engineering recommendations, not evidence that a particular ComfyRizz output passed.
